## 4. The Patterns Worth Surfacing for Process

### 4.1 The closure-absorption ratio is real and growing

Epic 6.5 was created with a 59% closure-absorption ratio (10 walk-discovered stories cleaved from Epic 6's 9-story mandate). Across the lifetime of Epic 6.5, 8 additional walk-discovered stories landed (6-12 through 6-21), pushing the final ratio to **~75% closure-absorption** (15 of 20 closure-shaped stories originated from prior-epic carry-forwards). The Epic 6 retro action item — "Epic 7's planning rubric will size by net-new only with an explicit closure-absorption budget line (15-20% reserve)" — needs revision: **the 15-20% reserve is too low**. Recommend **30-40% reserve** based on Epic 6.5 data, OR an explicit policy that walk-discovered defects spawn a new epic (6.5-style) rather than being absorbed into the next planned epic.

### 4.2 The privacy-invariant gate-placement bug class

F28 (sensitivity gate at wrong architectural layer) is the most consequential finding of the entire MailBot project to date. The bug class: **invariants enforced at a specific code path can be silently bypassed when the deployment uses a different code path that touches the same data**. Story 4-7's sensitivity-handshake invariant was enforced at the `ask_router(task_type="draft_reply")` site; Hermes's production flow drafts via `chat_completions_tool_call` (the F11/Story 6-9 path), which doesn't go through `ask_router`. The gate fired on a code path that, in the live deployment, was never reached.

**Three implications worth recording:**

1. **Phase 3.5 walks against the real Hermes runtime are not optional.** Unit tests of Story 4-7 stayed green across the entire F28 window. Integration tests of `ask_router(draft_reply)` stayed green. The bug was only visible when an actual Hermes runtime exercised the actual production code path against an actual sensitive fixture. The fifth-pass walk's `router_calls.id=6444` evidence (`caller_origin=unknown-external`, `task=chat_completions_tool_call`, sensitive body in main-inference Haiku context) is the canonical example of a defect a thousand unit tests cannot catch.

2. **Adam's option-A strictest-placement decision is the right pattern for privacy-invariant gates.** The decision: gate ALL `chat_completions_tool_call` when ANY referenced email is sensitive/confidential, not just the parameter. The sixth-pass walk proved this is provably MORE aggressive than the bare F28 fix — the CP-C conversation-history-bleed scenario (sensitive email_id from prior turn still in message history) triggered the gate immediately on the new turn, before Hermes could even attempt `find_emails` for the confidential fixture. Conservatism at privacy boundaries is the right call.

3. **Defense-in-depth is the architectural answer to gate-placement bugs.** The fix preserved Story 4-7's `ask_router(draft_reply)` gate UNCHANGED (6 existing tests green unmodified). Plus the new multi-id gate at `dispatch_tool_call`. Plus the SKILL.md Rule Q persona-layer guidance. Plus the v3 prompt module's confidential discipline. Plus the existing `hydrate_email` verb-layer refusal for confidential. **Five gates against the same threat.** Each gate independently sufficient; collectively, no single layer regression can compromise the invariant.

### 4.3 The sibling-quartet / inline-fix-and-walk loop scales to a sibling-octet

Epic 6's sibling-quartet (F6/F7/F8/SKILL.md) was the first instance of this pattern: live walk surfaces a contract mismatch → root-cause investigation → minimal-scope fix → regression tests → live re-walk → next bug surfaces. Epic 6.5 extended it: the third-pass walk surfaced F19/F22 (closed inline) + F21/F23 (filed as backlog); the fourth-pass walk surfaced F24/F25/F26 (filed as backlog); the fifth-pass walk surfaced F27/F28/F29 (filed as backlog — F28 CRITICAL); the sixth-pass walk surfaced F30/F31 (filed as Epic 7 carry-forward). **The pattern is now structurally proven across 8 fixes spread over 4 walks.**

**Operational implication:** the live walk is itself a debugging tool, not just a verification step. The 6-pass walk sequence on Story 6-6.5 was not "we kept failing" — it was the **structured discovery loop** that turned a vague "the system works on test fixtures" into "the system works against real Hermes against real Outlook against real Discord with real privacy invariants holding under real adversarial inputs." Each pass shipped 1-3 stories. The cadence is sustainable and high-yield.

### 4.4 The Hermes-flow signal-expressivity gap is the next-largest architectural debt

F30 + F31 + the CP-C tone-drift sub-finding + the CP-B mint-then-stall behavior all share root cause: **mailbot-api returns terminal states (refused / requires-grant / sensitivity-blocked / dispatched / drained) without a structured "next-step" signal Hermes can use to drive the agent forward.** Hermes infers next-steps from SKILL.md + AGENTS.md + SOUL.md + main-inference Haiku's training prior. Inference works most of the time. When it fails, the failures are non-obvious because the agent stays plausible (drafts a reply that looks reasonable, picks an action_type that looks reasonable, gives up at a stall point that looks reasonable).

**The fix-shape is consistent across F30/F31/tone-drift/mint-stall:** every refusal/blocked/terminal response should carry a `recovery_action: {tool_name: str, args_hint: dict, user_facing_guidance: str | None}` field. Hermes parses it; agent acts on it; no inference required. This is **Epic 7 architecture work** — touches every verb response shape, the propose_action error contract, the router refusal shapes, and likely a new MCP resource or two. Not for absorption into eval/calibration scope.

### 4.5 CR cadence stays at 100% applied-rate — 3 consecutive epics, no skill-level enforcement

Epic 4: 100% applied-rate. Epic 5: 100% applied-rate. Epic 6: 100% applied-rate. **Epic 6.5: 100% applied-rate** (121 of 121 actionable findings across 15 MANDATORY-CR stories). The CR cadence v2 rule (`feedback_cr_cadence_v2_structural.md` + memory) holds via human discipline + reference doc, without the formal autonomous-epic-run skill amendment. **C5 should be formally closed as CLOSED — operationally redundant.**

## 8. Significant Discoveries (this retro)

### 8.1 The 6-pass walk sequence is the structural backstop, not a bug

Story 6-6.5 was walked 6 times (passes 3 through 6 documented in run-flags). Each pass surfaced 1-3 new findings. Each finding closed before the next pass. The cumulative effect: **a single walk story produced 11 of Epic 6.5's 18 stories** (the inline-fix-and-walk fallout). This is not "we kept failing the walk"; this is **the walk IS the discovery mechanism**. Epic 6's retro identified Phase 3.5 cadence (C6) as a structural backstop carry-forward; **Epic 6.5 demonstrates that the cadence IS in place operationally, just not codified**. The 6-pass sequence on a single capstone story is the strongest evidence yet. Recommendation: stop treating C6 as a debt item; recognize the walk-discovery loop as the de facto Phase 3.5 mechanism.

### 8.2 Privacy-invariant gate-placement is the highest-risk bug class in MailBot

F28 (sensitivity gate at wrong architectural layer) is the most consequential single finding in MailBot's history. The bug: Story 4-7's gate guarded a code path that the live deployment never reached. Detection required a live Hermes runtime exercising the actual production path against an actual sensitive fixture. The fix (Story 6-20) was correct, applied at the strictest placement (Adam's option A), and verified live in CP-B. **But the lesson is broader: every privacy invariant in MailBot needs to be cross-referenced against ALL code paths that touch the gated data, not just the path the spec assumed.** Recommendation for Epic 7+: any new privacy-invariant gate gets a mandatory "code path enumeration" checklist as part of its AC — what are ALL the entry points that touch this data, and is the gate enforced at each? This would have caught F28 at Story 4-7 design time.

### 8.3 The closure-absorption reserve estimate was wrong by 2x

Epic 6 retro estimated 15-20% closure-absorption reserve for Epic 7 planning, based on Epic 6's 59% data point (which was already high). Epic 6.5 closed at **75% closure-absorption** (15 of 20 closure-shaped stories originated from prior-epic carry-forwards). The 15-20% estimate is wrong by 2x or worse. Recommendation: revise to 30-40% reserve, OR adopt the explicit policy "walk-discovered defects spawn a new N.5 epic rather than being absorbed into the next planned epic." The latter is operationally cleaner (Epic 7's identity as eval & calibration stays clean) and matches what Epic 6.5 actually demonstrated (the scope-cleave decision produced a coherent epic with measurable scope, not a contaminated next epic).

### 8.4 The OAuth-token chat-leak incident (memory) is now load-bearing for future re-auth walks

During the F23 re-auth walk (fourth pass), a refresh token leaked into chat output and required immediate revocation + re-mint. The lesson was captured in memory as `feedback_oauth_token_handling.md`: walk Adam through copy-to-file in a text editor; never paste token output into chat. This memory is now part of the standard OAuth re-auth runbook context. Recommendation: codify the memory into the Story 6-15 runbook (`docs/auth-recovery-runbook.md`) as a top-of-file SAFETY callout, so the discipline isn't memory-resident only.
