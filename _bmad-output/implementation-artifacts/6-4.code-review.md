# Story 6-4 Code Review: Anti-fatigue mechanics

## Verdict

**Changes Requested**

## Summary

The anti-fatigue gating layer is well-structured and mostly correct, but one real data-loss bug was found in the dedup path: the count query includes already-delivered rows, so when 5+ notifications for a category have already been acked (`delivery_status='ok'`), the 6th call within the same hour collapses to an UPDATE that silently touches 0 rows — the notification is dropped with no INSERT and no delivery. All other findings are lower severity (observability, semantic documentation, minor audit gap).

---

## Action Items (ordered by severity)

---

### 1. HIGH | PATCH | `mailbot_api/db/queries.py:1009–1012` + `mailbot_api/notifications/tiers.py:100–122, 162–183`

**Issue: Dedup count includes already-delivered rows — silent data loss when 5+ notifications have been delivered in the past hour.**

`NOTIFICATIONS_OUTBOX_COUNT_SAME_CATEGORY_LAST_HOUR` counts ALL rows matching `category + tier + enqueued_at >= cutoff` — it does NOT filter by `delivery_status`. `NOTIFICATIONS_OUTBOX_UPDATE_LATEST_MESSAGE` only updates rows WHERE `delivery_status = 'pending'`.

Walk the failure path: Adam receives 5 urgent `health` alerts within 30 minutes; Hermes delivers and acks all 5 (status transitions to `'ok'`). 10 minutes later, a 6th `health` alert fires (sync still stale). `should_dedup` returns `(True, 5)` (count=5, max_id=5). The dispatcher calls `execute_write(UPDATE ... WHERE id=5 AND delivery_status='pending')` — but row 5 is `'ok'`. The UPDATE matches 0 rows. No new row is inserted. The alert is **silently dropped**. Adam never sees it. The only trace is the `notification.dedup.collapsed` log event, which an operator monitoring from the inside might catch, but the notification is gone.

This is a real correctness bug — `delivery_status='ok'` rows should not count toward the dedup window because they can never be rewritten.

**Suggested fix — two-part:**

1. Add `AND delivery_status = 'pending'` to the count query so it only counts rows still in-flight:
   ```sql
   -- queries.py
   NOTIFICATIONS_OUTBOX_COUNT_SAME_CATEGORY_LAST_HOUR = (
       "SELECT COUNT(*), MAX(id) FROM notifications_outbox "
       "WHERE category = ? AND tier = ? AND enqueued_at >= ? "
       "AND delivery_status = 'pending'"
   )
   ```

2. Add a defensive guard in the dispatcher (tiers.py) for the case where `latest_id` resolves to a row that is already non-pending (concurrent race). After the UPDATE, check `execute_write` rowcount; if 0, fall through to the normal INSERT. This is belt-and-suspenders against the still-possible race where a row transitions to `'delivering'` between the count and the UPDATE:
   ```python
   rowcount = await connection.execute_write(
       db_path,
       queries.NOTIFICATIONS_OUTBOX_UPDATE_LATEST_MESSAGE,
       (summary, latest_id),
   )
   if rowcount == 0:
       # Collapse target was already delivered — fall through to new INSERT.
       # (Log the miss so ops can see it.)
       logger.warning("dedup collapse missed (row already delivered), inserting new row", ...)
       # ... fall through to the INSERT below
   else:
       logger.info("notification dedup collapsed", ...)
       return
   ```

**Reasoning:** This is the only finding that causes message delivery failure with no recovery path. Urgent notifications triggering this path (e.g. sync-stale during an active incident) would go missing silently.

### 2. MED | PATCH | `mailbot_api/notifications/tiers.py:71`

**Issue: `_log_suppressed` uses `logger.info` for dropped notifications — suppressed alerts are unfindable in a WARNING-filtered log stream.**

An operator searching "why didn't Adam get this alert" would look at WARNING-level logs, not INFO. All four suppression events (`notification.muted`, `notification.posture.suppressed`, `notification.quiet_hours.dropped`, and `notification.dedup.collapsed`) go through `_log_suppressed` at INFO level, or inline `logger.info` in the dedup path.

**Suggested fix:**
```python
# tiers.py:71
def _log_suppressed(event: str, tier: str, category: str, message: str) -> None:
    logger.warning(   # was: logger.info
        f"notification {tier} dropped",
        extra={...},
    )
```

Also change the dedup `logger.info("notification dedup collapsed", ...)` calls in `send_urgent` (line 113) and `send_important` (line 175) to `logger.warning`.

**Reasoning:** Suppressed notifications are operationally significant events — they explain why Adam did not receive an alert. INFO-level is appropriate for normal delivery; WARNING is appropriate for intentional suppression, especially for the mute and posture paths where a misconfiguration (typo in category name, posture inadvertently left active) would be invisible at INFO.

Exception: `notification.quiet_hours.dropped` for the informational tier could stay INFO since informational is log-only anyway — dropping it is not an operational concern. But the other three (muted, posture.suppressed, dedup.collapsed) warrant WARNING.

### 3. MED | DECISION | `mailbot_api/notifications/tiers.py:90–99` + story AC + `tests/integration/test_fatigue.py:75`

**Issue: Urgent messages honor mute — this contradicts FR-7.4 ("urgent means urgent") and the story's own critical guardrail.**

The story's Critical Guardrails section explicitly states: `"DO NOT drop urgent messages for ANY reason except mute."` — which means the dev intentionally interpreted mute as an exception to the urgent-always-delivers invariant. The story AC says urgent "bypasses quiet hours + posture" but is silent on mute.

The dev's rationale is quoted in the completion notes: "even urgent honors mute. Adam asked for the category to be quiet." The test (`test_mute_blocks_urgent`) validates this behavior.

**The risk:** If Adam mutes `health` during a noisy period and a real `health` emergency fires (worker process down, sync stale), the alert is silenced. Unlike quiet hours (which has a known 08:00 wakeup) or posture (which Adam lifts via `/resume`), a mute has no automatic expiry unless `muted_until` was set. An indefinite mute on `health` means Adam is blind to real health emergencies until he manually runs `/unmute health`.

**This is a DECISION that must be explicit.** The current behavior is defensible if Adam wants full control; it is dangerous if he might mute `health` casually and forget.

**Suggested action:** Require Adam to confirm this choice. One option: make the mute gate skip `tier='urgent'` (align with FR-7.4); another is to document the current behavior prominently in the story and in `unmute_category`'s docstring as a known sharp edge.

**If behavior is confirmed as intended:** Add a docstring note to `send_urgent` at line 91 and to `mute_category` at its description: `"Note: mute silences ALL tiers including urgent. Use with care on categories like 'health'."` Also add a test confirming urgent-muted-health does NOT deliver. The test exists (`test_mute_blocks_urgent`) but its comment says "Adam asked for the category to be quiet" — the comment does not reference the risk.

All quiet-hours tests only call `is_quiet_hours` as a unit test — there is no integration test for "send_important at 23:00 → row IS in outbox." ### 6. LOW | PATCH | `mailbot_api/notifications/posture.py:82–96`

**Reasoning:** Low because the DB column can be added later without breaking anything. But the asymmetry (set records reason, lift records nothing) will become confusing when Story 6-9's auto-trigger lands.

### 8. LOW | DECISION | `mailbot_api/db/queries.py:1036–1038`

**Issue: `POSTURE_STATE_LIFT_URGENT_ONLY` clears `set_at` — the record of WHEN the posture was activated is lost on lift.**

When posture is lifted, `set_at` and `reason` are both set to NULL. If anyone queries `SELECT * FROM posture_state` after a lift, they see `urgent_only=0, set_at=NULL, reason=NULL` — same as the initial seeded state. There is no way to distinguish "never activated" from "activated and then lifted."

This is acceptable for a single-row singleton table where only the current state matters, and the activation event was already logged. However it means the `get_posture()` API returns a shape that cannot represent the lifted state differently from the never-set state.

**Suggested action:** Accept as-is for now (this is a known trade-off of the single-row singleton pattern) or add `lifted_at` column (see finding #6 above). Document the "cleared on lift" semantics explicitly in the SQL comment.

## Non-findings (probed, assessed clean)

**Dedup race (double UPDATE, cosmetic flicker):** As the dev noted, two concurrent `send_urgent` calls both seeing count=5 and both calling `UPDATE ... WHERE id=N AND delivery_status='pending'` is a benign idempotent overwrite — the summary message is identical, and SQLite's WAL mode serializes writes. The second UPDATE just confirms the same value. The TWO `notification.dedup.collapsed` log events are a cosmetic operational annoyance but not a correctness issue. No data loss (finding #1 above is a different scenario — delivered rows, not racing pending rows).

**Posture lift race (two concurrent /resume, both return posture_lifted=True):** Cosmetic. Two "lifted urgent-only posture" messages in the response are odd but not harmful. The DB ends up correct (urgent_only=0). Acceptable for a single-user system.

**`send_informational` API-breaking change (sync→async):** Verified clean. `grep send_informational` across all `.py` files finds only: `tiers.py` (definition), `notifications/__init__.py` (mention in docstring, no call), and `test_notification_delivery.py` (one test, updated to `await`). No production callers. The optional `db_path=None` parameter preserves backward compatibility for any sync caller that doesn't pass it.

**`is_muted` ISO string format mismatch:** `mute_category` stores `muted_until` as `"%Y-%m-%dT%H:%M:%SZ"` (no microseconds). `is_muted` compares against `"%Y-%m-%dT%H:%M:%S.%fZ"` (with microseconds). Since the stored value ends in `Z` and the comparison string ends in `.µµµµµµZ`, and `"."` (0x2E) < `"Z"` (0x5A) in ASCII, the comparison `muted_until > now_iso` is correct: a future-dated stored value (e.g. `"2026-06-09T00:00:00Z"`) will correctly be `>` the current time string regardless of the format difference, because the date portion differs. The only case that could go wrong is `muted_until = now_iso` to-the-second, in which case the stored value `"...00Z"` compares less than `"...00.000001Z"` — meaning a just-expired mute would be treated as expired (not muted). That is the correct behavior. **Clean.**

**`muted_until=None` → SQL NULL path:** `mute_category` accepts `muted_until: str | None = None` and passes it directly to `NOTIFICATION_MUTES_UPSERT` as the second parameter. Python `None` maps to SQL `NULL` via the sqlite3 adapter. `is_muted` then reads `row[1]` and returns `True` if `muted_until is None`. Confirmed working in `test_mute_category_indefinite_uses_null`. **Clean.**

**Quiet-hours boundary asymmetry (22:00 inclusive, 08:00 exclusive):** `hour >= 22 or hour < 8` — 22:00 IS quiet, 08:00 is NOT. This matches the test `test_is_quiet_hours_boundary_08_utc_is_false` explicitly. The boundary semantics are documented in the test comment. For a system that starts delivering at 08:00, this is correct — 08:00 itself should deliver. **Clean.**

**Migration `020_posture_state.sql`:** Single-row table with `CHECK (id = 1)` constraint and `CHECK (urgent_only IN (0, 1))` — solid pattern matching `degraded_mode_state`. `INSERT INTO posture_state (id, urgent_only) VALUES (1, 0)` seeds the row. No `IF NOT EXISTS` needed since the migration runner tracks applied migrations. **Clean.**

**MCP tool `unmute_category` registration:** 20th tool correctly registered. `_EXPECTED_TOOL_COUNT = 20` assertion is correct and will fail-fast on mismatch. `_TOOL_DESCRIPTIONS` entry present. **Clean.**
