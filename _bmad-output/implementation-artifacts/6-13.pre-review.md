If the UPDATE fails (e.g., DB locked under contention), the entire `mint_grant` call propagates the exception to the caller AFTER the ACTION_GRANT_INSERT already succeeded — leaving an asymmetric state (grant minted but promotion not done). The drainer would still recover on the next tick because `is_grant_valid` would now return True for the new grant, but the failure mode is silently latent in the API surface. **Severity:** LOW because (a) SQLite WAL contention is rare on a single-writer process, (b) the drainer self-heals on the next tick. **Disposition:** ESCALATE TO REVIEWER — get a second opinion on whether to swallow + log the exception inside `mint_grant`, or whether the current loud-fail behavior is preferable (loud-fail surfaces DB contention bugs early).

A truly load-bearing counter-test would seed multiple rows (some of matching type, some of mismatching type) and assert ONLY the matching ones promoted. The existing `test_mint_grant_promotes_multiple_matching_rows` covers the "multiple matching promote" half, but a combined "mixed types in DB, only matching promote" test would be sharper. **Severity:** LOW — current coverage is sufficient; the SQL filter is explicit. **Disposition:** ACCEPT WITH RATIONALE — current 6 tests cover the lattice; the proposed combined test would be redundant in practice.
