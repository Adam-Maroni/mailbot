Acceptable, but flag for reviewer confirmation that "removed_reason='deleted' without move-family cross-check" is the right guard granularity.
- [MEDIUM] `mailbot_api/actions/replay.py` — the new move-family `target_deleted` refusal reads `EMAIL_SOFT_DELETE_STATE_SELECT` and treats `email_state is None` (row entirely absent) as `target_deleted=True`. If a move-family row's email_id somehow points to a never-synced email, the operator gets `REPLAY_MOVE_TARGET_DELETED` directing to `revert` — but `revert` would then hit `PRE_STATE_MISSING`. Minor: the two refusals chain to a dead-end for that edge. Real-world: move-family rows always have a synced source email (the move acted on it), so this is a defensive-only path. FIX assessment below.

Safe today because only static-map inverses reach it (move-family with absent history refuses PRE_STATE_MISSING first) and static-map inverses don't consult pre_state. Flag for reviewer to confirm no future consumer reads the placeholder.
- [LOW] `scripts/mailbot.py` — removed `_load_policy_for_cli`; confirmed no other caller (grep clean). The `init_pipeline_runtime` path applies pending migrations + inits budget/pause, which the old helper did NOT — a slightly heavier init for rederive, but correct (matches pipeline CLI + worker). No behavioral regression; the extra init is idempotent.
