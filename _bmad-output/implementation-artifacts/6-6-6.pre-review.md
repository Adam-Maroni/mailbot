## Verdict

**MANDATORY-CR.**

The §5.12 rule fires at 3+ criteria, but #5 alone is sufficient here as an explicit MANDATORY surface (load-bearing transport seam where 5+ downstream stories assume the fix is correct). The combination of #2 + #5 + the "tests-pass-at-the-call-boundary-not-the-transport-boundary" pattern (already a documented Epic 6 retro lesson from Story 6-8's HIGH-1 PNG-bytes JSON serialization catch) makes adversarial review especially valuable.

Notable structural risk surfaces a fresh reviewer should grade adversarially:

1. **Two-part fix interdependence.** The server-side `streamable_http_path="/"` AND the client-side trailing-slash URL are BOTH required. Either one alone leaves F6 partly open. The 4 regression tests cover both halves, but the reviewer should confirm: if a future operator drops just one half, do the tests catch it? (The config-shape test does for the client side. The structural test does for the server side. The two E2E tests assert combined-state success.) Are there edge cases where only one half breaks and the tests pass?
2. **FastMCP version-bump risk.** `streamable_http_path` is FastMCP-library-internal — version 2.x could rename it. The structural test asserts the value via `server.settings.streamable_http_path == "/"`, so a rename would fail the test (assuming the setting STILL exists under a new name; if it's removed entirely, the FastMCP construction itself fails first). Reviewer should grade: is the structural test the right level of abstraction?
3. **Mount + trailing-slash interaction.** FastAPI's Mount semantics + `redirect_slashes=True` (default) is the root cause of the client-side half. The fix accepts the 307 and just points Hermes at `/mcp/` directly. Alternative: set `redirect_slashes=False` on the FastAPI app or on the Mount specifically. The DECISION made (point Hermes at the slash) is documented but the alternative isn't sketched in the fix code — should the inline comment block sketch the trade-off?
4. **E2E test coverage gap.** The two E2E tests fire against `TestClient` (in-process httpx). Real Hermes runs in a separate container. The transport-security warning observed during testing (`Invalid Host header: testserver`) suggests there are middleware layers between FastAPI Mount and the MCP handler that the in-process tests don't exercise faithfully. Is the regression coverage actually catching the real-world behavior?
5. **Hermes-side behavior assumption.** Story 6-0 walk recorded "Hermes's MCP client doesn't follow 307 redirects on the bidirectional POST transport." The fix assumes this. If a future Hermes version DOES follow 307s on POST, the trailing-slash URL is still correct (no regression). If it doesn't, the fix as shipped works. Either way safe — but the reviewer should confirm the assumption is documented somewhere a future operator would find it.
6. **`scripts/check_hermes_config.py` consistency.** The constant `_EXPECTED_MCP_URL` was updated; the corresponding inline check in the script still works because string equality. Reviewer should confirm the message printed on mismatch is still useful (does it say "trailing slash required" or just print the diff?).
7. **Migration story for an existing deployment.** If an operator already has a deployed Hermes container with the old `/mcp` URL, what happens? They'd see the 307 → 404 chain (the original F6 symptom). The Story 6-7 setup-vps runbook doesn't yet document the F6 closure or call out the URL shape as load-bearing. Should this story update the runbook?
