## 3. Action Items

### HIGH-1: `PullPendingNotificationsOut.count` is a stale independent field, not derived — desync is confirmed reproducible

- **Severity:** High
- **Type:** PATCH
- **File:line:** `mailbot_api/verbs/pull_pending_notifications.py:43-49`
- **Issue:** `PullPendingNotificationsOut` declares `count: int = 0` as an independent field with a default of `0`. A caller that constructs `PullPendingNotificationsOut(notifications=[n1, n2])` without explicitly setting `count` gets `count=0` and `len(notifications)=2` — silently desynchronized. This was confirmed against the live codebase: running `PullPendingNotificationsOut(notifications=[PendingNotification(...)])` returns `count=0`. Hermes reading `decoded["count"]` from the MCP response would see `0` while the list has items — or vice versa if a future code path forgets to set `count`. The production path in `pull_pending_notifications` at line 113 does correctly pass both, so the bug is latent not active, but it is a time bomb for any future refactor that touches the constructor call.
- **Suggested fix:** Use a Pydantic `computed_field` / `@property` or derive count from the list at construction time using a validator. The cleanest Pydantic v2 approach:

  ```python
  from pydantic import BaseModel, Field, model_validator

  class PullPendingNotificationsOut(BaseModel):
      notifications: list[PendingNotification] = Field(default_factory=list)
      count: int = Field(default=0)

      @model_validator(mode="after")
      def _sync_count(self) -> "PullPendingNotificationsOut":
          self.count = len(self.notifications)
          return self
  ```

  Or remove `count` entirely and let callers use `len(out.notifications)` — it is accessible over the MCP wire in the decoded `notifications` array anyway.

- **Reasoning:** Redundant derived fields in Pydantic that can fall out of sync are a silent correctness hazard. The test at line 289 (`decoded["count"] == 1`) passes only because the production code happens to set it correctly. A future caller of the shape that forgets `count=len(claimed)` produces incorrect output with no exception.

### HIGH-2: `ack_notification` failed path has a TOCTOU between the `fetchone` (to read `attempt_count`) and the `execute_write` — recovery can flip state in between, causing misrouted ack path

- **Severity:** High
- **Type:** PATCH
- **File:line:** `mailbot_api/verbs/ack_notification.py:96-145`
- **Issue:** The `delivery_status == "failed"` branch does:
  1. `fetchone` to read `attempt_count` from the row (line 96)
  2. Python-side `if attempt_count >= 5` branch selection (line 111)
  3. `execute_write` with the chosen UPDATE SQL (line 112 or 141)

  Between steps 1 and 3, the recovery sweep can flip the row from `delivering` to `pending`. When that happens, the `execute_write` at step 3 returns `rowcount=0` (because `WHERE delivery_status='delivering'` no longer matches), which is handled correctly by the `if rowcount == 0` fallback at lines 117/146.

  The actual bug is subtler: **both** `NOTIFICATIONS_OUTBOX_ACK_FAILED_RETRY` and `NOTIFICATIONS_OUTBOX_ACK_FAILED_MAX` re-assert `AND delivery_status='delivering'` in the SQL (confirmed in `queries.py:962,970`). This means the Python-side routing based on the pre-race `attempt_count` is redundant — the SQL itself also asserts `AND attempt_count < 5` / `AND attempt_count >= 5`. So if recovery flips the row between the read and the write, the write returns `rowcount=0` and the `if rowcount == 0` path fires correctly.

  However, there is a subtler case: the recovery sweep does NOT update `attempt_count` (confirmed in `NOTIFICATIONS_OUTBOX_RECOVERY_RECLAIM`, line 980: only `delivery_status` is set back to `pending`). So after recovery, the row has `delivery_status='pending'` and `attempt_count` stays at whatever it was bumped to by the pull. If the ack's `fetchone` reads `attempt_count=4` (under cap) but between the read and write, recovery flips it to `pending`, and THEN a new pull happens (bumping to `attempt_count=5`), the ack's Python-side branch routes to retry path and tries `NOTIFICATIONS_OUTBOX_ACK_FAILED_RETRY` (with `AND attempt_count < 5`) — but the row now has `attempt_count=5`, so the SQL also returns `rowcount=0` and falls to `_fetch_status`. This is handled correctly but **silently**. The last_error from this ack attempt is discarded.

  The deeper concern: if recovery happens exactly at t=60.1s, and ack arrives at t=60.2s, the ack returns `ok=False, final_status='pending'` — which signals to Hermes that the notification is back in pending. But Hermes has no feedback that its error message was NOT persisted. If the ack failure reason matters for debugging, it is silently lost.

- **Suggested fix:** Document this gap explicitly in the verb docstring. Add a warning log when `rowcount=0` in the failed path that includes the error text so the lost reason is at least observable:

  ```python
  if rowcount == 0:
      current = await _fetch_status(db_path, notification_id)
      logger.warning(
          "ack failed rowcount=0 — recovery race; error discarded",
          extra={
              "event": "notification.ack.race_loss",
              "notification_id": notification_id,
              "discarded_error": error_text or None,
              "current_status": current,
          },
      )
      return AckNotificationOut(...)
  ```

- **Reasoning:** The error text passed by Hermes on a failed delivery is operationally valuable (Discord 5xx, rate limit detail, etc.). Silent discard on recovery races leaves no trace in logs. The warning log makes the gap observable without changing the correctness model.

### MED-1: `_fetch_status` returns `"unknown"` for `delivery_status='delivering'` — incorrect in the recovery-race scenario where the row is still in `delivering`

- **Severity:** Med
- **Type:** PATCH
- **File:line:** `mailbot_api/verbs/ack_notification.py:170-183`
- **Issue:** `_fetch_status` returns `"unknown"` if the row's `delivery_status` is `"delivering"` (the only non-listed status at line 181). The `AckNotificationOut.final_status` type is `Literal["ok", "pending", "failed_max_retries", "unknown"]` — `"delivering"` is not in that Literal, which is correct. But the semantics are wrong: if `_fetch_status` is called because the ack found `rowcount=0`, and the row is STILL `"delivering"` (e.g., a race between two concurrent ack calls where one won), the caller gets `final_status="unknown"` even though the row is deterministically in `"delivering"` state. `"unknown"` suggests "not found" semantics; `"delivering"` means "someone else already acked it or a second pull happened."

  This misleads Hermes, which would interpret `"unknown"` as "row might not exist" rather than "the row is mid-delivery by someone else." The distinction matters for whether Hermes should retry or investigate.

- **Suggested fix:** Either extend the `AckNotificationOut.final_status` Literal to include `"delivering"`:
  ```python
  final_status: Literal["ok", "pending", "failed_max_retries", "delivering", "unknown"]
  ```
  And update `_fetch_status` to return `"delivering"` for that case. Or add a specific log line distinguishing `delivering`-state mismatch from `None`-row mismatch.

- **Reasoning:** `"unknown"` conflates two different conditions — row deleted and row in-flight. Hermes's decision logic should distinguish them.

### MED-2: Stale/false docstring in `outbox_recovery.py` — claims 60s is "shorter than" 50s

- **Severity:** Med
- **Type:** PATCH
- **File:line:** `mailbot_api/notifications/outbox_recovery.py:8-10`
- **Issue:** The module docstring reads:

  > "The 60-second window is intentional: shorter than Hermes's pull cadence multiplier (10s × 5 attempts = 50s) by a small margin, so a single Hermes hang of less than 1 minute doesn't cause re-pull."

  This is factually wrong on two counts:
  1. 60 is not shorter than 50 — it is LONGER. The threshold is designed to tolerate short hangs; 60 > 50 is intentional but the comparison is stated backwards.
  2. The logic is also wrong directionally: the threshold is designed so that a Hermes hang of up to 60s does NOT trigger re-pull. "10s × 5 attempts = 50s" appears to be an attempt to reason about normal delivery time, but it is not explained and does not follow.

- **Suggested fix:**

  ```python
  """
  The 60-second window is intentional: a normal Hermes delivery attempt
  (pull → Discord post → ack) typically completes within ~15 seconds.
  60 seconds is chosen to be well above that to tolerate transient
  Discord API slowness or a Hermes restart, without waiting so long
  that a hard Hermes crash leaves messages silently stuck. Story 6-4
  may tune this after observation.
  """
  ```

- **Reasoning:** A false docstring is worse than no docstring — it will confuse the next reader (and the next dev agent) who tries to reason about the threshold value.

## 4. Probe results on the 9 self-audit surfaces

For completeness, disposition of all 9 dev-identified surfaces:

1. **Atomic claim race-safety.** The per-row claim pattern (`fetchall` then per-row `execute_write` with `WHERE delivery_status='pending'`) is correct under SQLite's BEGIN IMMEDIATE. Two concurrent pulls that both `fetchall` the same candidate set will then race on the per-row `execute_write`. Only one can hold BEGIN IMMEDIATE at a time; the second's UPDATE sees `delivery_status='delivering'` (committed by the first) and returns rowcount=0. The code correctly skips on rowcount=0. The failure mode described in the brief ("could a row be returned in both candidate sets?") — yes, it can appear in both initial `fetchall` results if both queries run before either write commits. But the per-row `execute_write` is the actual serialization point. **No bug here; documented correctly in the verb.**

2. **5-attempt boundary.** Walk: fresh row has `attempt_count=0`. Pull bumps to `1`. Ack-failed with `attempt_count=1` (< 5): retry path, back to `pending`. Pull bumps to `2`. ... 5th pull bumps to `5`. Ack-failed with `attempt_count=5`: terminal path. Row gets exactly 5 delivery attempts before `failed_max_retries`. **Off-by-one concern is unfounded — the cap is exactly 5.**

3. **Recovery-vs-ack race.** Confirmed the `rowcount=0` fallback path fires correctly but silently discards the error text. Escalated to HIGH-2 above.

4. **Legacy JSONL writer.** `send_urgent` in `mailbot_api/notifications/__init__.py` is still directly used by `test_send_urgent_writes_jsonl` — not dead code. The rationale ("backwards compat for one epic") is defensible IF there is a test exercising it. There is. However, the docstring in `tiers.py` at line 34 says the forwarder "re-dispatches into `tiers.send_urgent` with `category='legacy'`" — this is FALSE. Reading `__init__.py:45-85`, the legacy writer still writes to JSONL directly; it does NOT forward to `tiers.send_urgent`. The docstring is a documentation lie. **Raise: the tiers.py docstring is wrong about what the forwarder does.** This is a LOW finding folded into LOW-1 scope.

5. **Drainer Tier-2 routing change.** AC-3 explicitly requires `_notify_failure` to route Tier-2 to `send_important`. This matches the implementation. Tier-2 failures previously went via the JSONL urgent stand-in; they now wait for the 08:00 digest. Whether Adam wants real-time Tier-2 failure alerts is a product decision not a code defect. The AC is satisfied. **No bug; user-visible behavior change is intentional per AC.**

6. **Recovery loop count=0 silence.** Recovery loop only logs when `rowcount > 0`. Healthy-case ticks are silent. This is intentional and operationally correct — noisy healthy-tick logs are worse than silence. **Not a bug.**

7. **MCP wrapper `delivery_status: str` no Literal.** Malformed `delivery_status='partial'` reaches the verb's `if delivery_status == "ok"` check (no match) and falls to the `# delivery_status == "failed"` else path. The `type: ignore[arg-type]` at `mcp_server.py:589` acknowledges this. Any non-`"ok"` string is treated as `"failed"`. This is implicit semantics but it does not cause a crash — the failed path correctly handles the row. The risk is that a mis-spelled `"ok"` from Hermes (e.g., `"OK"`) silently treats a success as a failure. LOW but deferred — adding a wrapper-level guard would require changing the MCP schema, which affects Hermes's tool description. Flag for Story 6-4.

8. **Non-transactional pull-then-claim.** Documented in the verb docstring. The worst case is "fewer rows returned than requested." Confirmed as acceptable and correctly handled. **No bug.**

9. **Test specificity regression in `test_spend_chart_command.py`.** `>= 17` instead of `== 19` is a regression in canary strength. The original had `== 17`. After Story 6-3 it should read `== 19`. The developer chose `>= 17` to "prevent test churn" but this loses the canary entirely. **Minor — add to LOW scope.** Suggest reverting to `== 19` rather than `>= 17`.

Additional finding escalated from surface 4: `tiers.py` module docstring at line 34 states the legacy forwarder "re-dispatches into `tiers.send_urgent` with `category='legacy'`" — but reading `notifications/__init__.py:45-85`, the function writes directly to JSONL with no call to `tiers.send_urgent`. The docstring is false. If the intent was to make it a forwarder, it wasn't implemented that way. If the intent was to keep it as a JSONL writer, the docstring is wrong. This does not affect runtime behavior (all actual call sites use `tiers.send_urgent` directly) but is a documentation lie that will mislead anyone reading the module docstring.
