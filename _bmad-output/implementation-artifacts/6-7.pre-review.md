## 3. Adversarial self-review

- **[HIGH]** `setup_vps.sh:install_docker` uses `apt-key`-style GPG via `gpg --dearmor -o /etc/apt/keyrings/docker.gpg`. On Ubuntu 24.04, `apt-key` is fully deprecated and the keyring-based pattern is correct, but a reviewer may suggest adding `--keyring` to the apt-source line for explicitness. Current pattern matches docs.docker.com 2025 instructions for Ubuntu 24.04. Acceptable.
- **[HIGH]** `setup_vps.sh:create_env_stub` uses `install -m 0600 /dev/null` + `cat > "$env_file"` which creates the file and THEN populates it via redirect. There's a microsecond window where the file is empty + mode 0600 — race-condition-safe enough for first-deploy (the file is on the operator's VPS; no concurrent writer). Acceptable.
- **[HIGH]** `deploy.sh` uses `ssh ... 'docker load < /tmp/mailbot-api.tar && ... && rm -f /tmp/mailbot-api.tar'` — the `rm` runs on the VPS via the same ssh invocation. If `docker load` or `docker compose up` fails, the `&&` chain aborts and the tarball stays on the VPS. Next deploy will overwrite it. Acceptable — small disk-space risk on repeated failed deploys.
- **[MEDIUM]** `backup.sh` SQLite snapshot path: `/tmp/mailbot-${DATE}.db` is created INSIDE the mailbot-api container via `docker exec ... sqlite3 ... ".backup '$DB_SNAPSHOT'"`, then `docker cp` copies it OUT. The trap cleans both up. **Edge case**: if `docker exec` fails (e.g., container not running), the trap tries to delete a snapshot inside a dead container — harmless but emits a confusing error. Acceptable per `|| true` in the trap.
- **[MEDIUM]** `backup.sh:prune_old_backups` uses `find ... -print0` + `while IFS= read -r -d ''` — POSIX-correct null-delimited iteration. The date arithmetic uses `$(( ($(date +%s) - $(stat -c %Y "$file")) / 86400 ))` which depends on integer division — files exactly at the boundary may be off by 1 day. Acceptable for backup pruning.
- **[MEDIUM]** `restore.sh:wait_for_health` polls `localhost:8000/health` — only works because the script runs on the VPS itself (mailbot-api binds to 0.0.0.0:8000 per docker-compose.yml). A reviewer may suggest `127.0.0.1` for explicitness. Both work; acceptable.
- **[MEDIUM]** `restore.sh:run_status_check` tries multiple CLI invocation paths (`mailbot`, `docker exec ... python -m mailbot_api.cli`, `docker exec ... python scripts/mailbot.py`). The first two don't exist as binaries (`mailbot-api.cli` is not a documented module; `scripts/mailbot.py` is the actual entry). Defensive but verbose. Acceptable.
- **[MEDIUM]** `test_deploy_scripts.sh` stubs the deploy/backup/restore lifecycle paths with `log "TODO(Phase 3.5): ..."` rather than actually exercising them. A reviewer may suggest at least the backup.sh path could be exercised by faking the container with a stub `sqlite3` binary on PATH. Defensible — the stubs ARE the @manual scope per AC; the documented Phase 3.5 surface is where Adam walks them.
- **[LOW]** `deploy.sh` calls `set -euo pipefail` then `${MAILBOT_IMAGE_TAG:-mailbot-mailbot-api:latest}` — the `-u` flag treats `MAILBOT_IMAGE_TAG` as undefined ONLY if the `${VAR:-default}` substitution wasn't used. The `:-` syntax correctly handles unset. ✓
- **[LOW]** `backup.sh` emits to BOTH stdout AND `$LOG_FILE`. If `/opt/mailbot/logs/backup.jsonl` doesn't exist (first run), `mkdir -p` in `emit_json` handles it. ✓
- **[LOW]** `setup_vps.sh` heredoc `.env` content includes `OUTLOOK_REFRESH_TOKEN=` even though `mint_refresh_token.py` (Story 1-9) is the documented way to GENERATE that value. A reviewer may suggest the stub should reference Story 1-9. Acceptable — `.env.example` already documents this.
