## 3. Adversarial self-review

- [MEDIUM] `scripts/register_discord_commands.py:222` — `cmd_apply` iterates payload commands and returns 1 on the first 4xx **without printing already-registered commands' IDs to a resumability log**. If Adam runs `--apply` and the 3rd of 5 commands 4xx's, he sees the first two "Registered /X → command_id=Y" lines on stdout and can grep them out — but there's no explicit "resumable from command N" affordance. **Impact for this story:** none — the payload is a one-element list, so partial-failure is impossible. **Future risk:** if Story 9.5.5 or later adds more slash commands, partial-failure semantics get load-bearing.
- [LOW] `scripts/register_discord_commands.py:107` — `_load_task_names` uses `sorted(...)` to make the task choice order deterministic. Deterministic is right for fixture stability, but the sorted order does not match `router/policy.yaml`'s task-declaration order (which reflects logical grouping — coarse_class first, then sensitivity_class, etc.). Discord displays choices in the declared order; Adam will see alphabetical `action_extraction` first instead of `coarse_class`. **Judgment call — accepting with rationale:** fixture stability outweighs cosmetic ordering in the Discord picker; if it bothers Adam post-walk, easy one-line fix.
- [LOW] `scripts/register_discord_commands.py:88-91` — `EXCLUDED_FROM_PERSIST_CHOICES: frozenset[str] = frozenset({"embedding"})` — good use of `frozenset` for §5.7 (module-level immutable container). But the comment cites "Story 9-4 AC-2" without a link and Adam may not remember that ruling. **Fix now:** add a docstring or extended comment naming why embedding is excluded (Router does not dispatch embedding via `ask_router`, so `force_model` is undefined).
- [LOW] `scripts/register_discord_commands.py:214` — `_auth_headers` sets `"Content-Type": "application/json"` on every request including GET (`cmd_delete_all` enumerate call), which is harmless (Discord ignores Content-Type on empty-body requests) but semantically loose. **Accept with rationale:** simplicity > pedantic strictness; the Discord API tolerates it.
- [LOW] `tests/unit/scripts/test_register_discord_commands.py:143-155` — `test_apply_missing_bot_token_exits_2` and `test_apply_missing_application_id_exits_2` use `monkeypatch.delenv(..., raising=False)`. If the pytest process happens to have `DISCORD_BOT_TOKEN` set at run time (e.g., someone sourced `.env` before running tests), the `raising=False` swallows the delete correctly, but the test doesn't assert the *combination* of both being absent — just each independently. **Accept:** covered functionally; the sequential env-var check in `_read_credentials` fails on the first missing var, so the tests exercise both branches.
- [INFO] `docs/runbooks/discord-slash-registration.md:47` — mentions `.gitignore` for `.env` is already in place "for MailBot" — I didn't verify that claim at audit time. **Fix now:** verify via `Grep '^\.env$' .gitignore` OR soften the claim to "your .env should be .gitignore'd" (advisory).
- [INFO] `.env.example:8-11` — new comment says "Not read by Hermes at runtime" — technically Hermes never reads any `MAILBOT_*` or `DISCORD_APPLICATION_ID` because MailBot and Hermes are separate processes reading different env files, but the phrasing might confuse a future reader who thinks the env var flows to Hermes somehow. **Accept:** the runbook Section 5 clears it up.
