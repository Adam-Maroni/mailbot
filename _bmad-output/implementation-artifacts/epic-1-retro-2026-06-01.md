## 2. What Went Well

- **Hard boundaries shipped before they could be violated.** Story 1-4 delivered the five Rule I/B/C/F/observability boundaries plus the AST-based `check_boundaries.py` *before* any story would tempt a violation. The boundary checker independently flagged a real Rule-C violation in Story 1-6 (embedded SQL literals in `oauth.py`), proving the gate works.
- **Middleware-Real-Bootstrap discipline held throughout.** Every database test ran against real on-disk SQLite via `tmp_path`. Every HTTP test used `httpx.MockTransport` at the boundary, not at the function level. 84 tests, zero mocked DB, zero mocked business logic.
- **Gate-coverage-only review (Stories 1-4 through 1-8) caught the same issue categories that per-story Sonnet review caught in 1-1 through 1-3.** No regression in quality from the cadence change.
- **Autonomous run was envelope-tight.** Zero mid-loop permission prompts after bootstrap. The Python + Docker permission envelope from PORTING.md was sufficient for all 8 stories.
- **Phase 3.5 caught what no other gate could.** Four packaging bugs (F-1: `scripts/` missing from Dockerfile, F-2: `procps` not installed, F-3: `PYTHONPATH` unset, F-4: `SecretMissing` not handled in CLI) — all integration-surface bugs the gates and code review wouldn't have reliably caught.

## 4. Key Insights

1. **Gates are the review surface once the boundary-enforcement story ships.** Empirical evidence from Stories 1-5 through 1-8: gate-coverage-only review caught the same issue categories as per-story Sonnet review. Story 1-6's SQL-literals-in-oauth.py incident is the canonical proof point.
2. **Phase 3.5 is a checkpoint cadence, not a one-time epic-completion gate.** Four packaging bugs Phase 3.5 caught lived in the Dockerfile + container-env interaction surface — neither gate-coverage nor per-story code review would have caught them reliably.
3. **Transaction-semantics stories need explicit partial-application crash tests at dev time.** Three of Story 1-3's review findings were one root cause (transaction boundaries with `executescript` + autocommit). A gate that exercises mid-migration crash → restart would have caught all three at dev time, not review.
4. **Deferred items need owners and deadlines at the time of deferral.** `epic-run-flags.md` did this discipline well for Epic 1; keep it.

## 13. Postscript (added 2026-06-01) — Azure docs review surfaced four correctness gaps

After the main retrospective concluded, Adam pointed out that the Outlook integration surface had not been examined during the brainstorming phase. He had separately archived the Microsoft Graph + Azure documentation under [`docs/external/learn-microsoft-azure/`](../../docs/external/learn-microsoft-azure/) (100 pages mirrored locally via the docs-archiver skill). Reading the S-tier pages (delegated auth, delta query overview, message resource, MIME, auth concepts, Python tutorial, choose-authentication-providers) against the implemented Epic 1 surface produced ten findings, four of which are correctness gaps that affect long-running production sync.

**The four correctness gaps:**

1. **F-1 (CRITICAL) — Refresh-token bootstrap had no owner.** Story 1-5 reads `OUTLOOK_REFRESH_TOKEN` from `.env`; Story 1-6 persists rotation. Neither story owns the *first* refresh token, which per the Graph docs can only come from a browser-based OAuth 2.0 Authorization Code flow with user consent. `docs/auth-recovery.md` waved at "re-mint refresh token on dev box" without specifying how. **Resolved by new Story 1-9** (`scripts/mint_refresh_token.py` + `docs/entra-app-registration.md`).
2. **F-3 (HIGH) — Message ID rotation + `changeKey` mislabeled.** `emails.change_marker` was specified as Graph's `@odata.etag`, but `@odata.etag` does not exist on the message resource — the version field is `changeKey`. Worse, Graph message IDs rotate on folder moves unless the request carries `Prefer: IdType="ImmutableId"`, which the implementation didn't. **Resolved by new Story 1-10**: add Prefer header, document column semantics without renaming (keep `change_marker` column name to avoid destructive migration).
3. **F-4 (HIGH) — Delta-token invalidation has no recovery path.** Graph documents two failure modes (`410 Gone` synchronization reset, `404 syncStateNotFound` after cache eviction) that require clearing the stored `delta_link` and restarting from a full resync. Story 1-7's worker would log the error, fire the alarm after 60 minutes, and alarm forever. **Resolved by Story 1-10's `_handle_delta_token_invalidation` helper + one-shot debounced urgent notification.**
4. **F-5 (MEDIUM) — `@removed.reason` collapsed.** Graph distinguishes `changed` (recoverable from deletedItems) vs `deleted` (permanent); Story 1-7 treated both identically. **Resolved by Story 1-10's `emails.removed_reason` column.** Epic 4's Tier-1 reverter will respect this distinction.

**Decisions confirmed (Adam approved all three):**

- Story 1-9 ships the bootstrap script + Entra app-registration recipe as its own story (not folded into `docs/auth-recovery.md` as a manual recipe). Rationale: refresh tokens get rotated unpredictably; the script will be re-used.
- Keep the `emails.change_marker` column name. Document via docstring that the stored value is Graph's `changeKey`. Avoids a destructive schema migration on data that real-tenant sync (post-1-9) will start populating immediately.
- Stick with hand-rolled httpx for the runtime `GraphClient` (do not migrate to MSAL or `msgraph-sdk`). Rationale: `httpx.MockTransport` testability is load-bearing for the Middleware-Real-Bootstrap discipline; the SDK's request-builder API doesn't expose a clean mock seam; we only use ~5 endpoints. Revisit if a 6th endpoint lands or if conditional-access challenge prompts become a real recovery surface.

**Architecture document patches (6, all landed as part of Story 1-10's AC-7 scope):**

1. § "OAuth refresh-token rotation (D9)" — now points at Story 1-9 as the bootstrap source of truth.
2. § "Sync ↔ Actions (D4 + D5 + D9)" Rule B — `Prefer: IdType="ImmutableId"` header invariant documented.
3. § "Schema implications introduced in this section" — `emails.change_marker` semantically aligned to `changeKey`; `emails.removed_reason` column added.
4. § "Sync ↔ Actions" write-back retry contract — delta-token invalidation recovery bullet added.
5. New § "Access model" — delegated access decision + tenant-value matrix (`consumers` / GUID / `common`) documented.
6. New § "Reference Material" appendix — `docs/external/learn-microsoft-azure/` registered as the canonical archived reference.

**Story 1-9 was the missing piece blocking Phase 3.5 CP-6/CP-7** (idempotent re-sync against a real tenant; send-yourself-test-email end-to-end). Without it, those checkpoints were structurally impossible because Adam had no documented path to populate the refresh token. Now they are explicitly unblocked.

**Critical-path update:**

- **Story 1-9 (CRITICAL)** — blocks any real Outlook sync; required before Phase 3.5 CP-6/CP-7 can be attempted.
- **Story 1-10 (HIGH)** — should complete before Epic 4 starts (Epic 4's Tier-1 reverter depends on `removed_reason`).
- Neither blocks Epic 2 (Router cost-discipline center) or Epic 3 (Ingest pipeline). Epic 2's Story 2.1 (`router_calls` audit table) remains the entry point and is independent of 1-9 and 1-10.

**Process lesson (the most important one):**

The docs-archiver skill exists. It was authored before MailBot's brainstorming phase started. We did not run it. Had we mirrored the Azure Graph docs **during** brainstorming, we would have found F-1, F-3, F-4, F-5 before Story 1-5 was written, and saved two stories of post-hoc patching. **Action item #8 (new, added post-retro):** for any future epic that integrates with a complex external API, run the docs-archiver as a mandatory preparation step before story planning. Owner: Adam (decision); Amelia (execution per epic). Trigger: epic touches a new external service surface beyond what's already archived. This becomes a standing rule going forward.
