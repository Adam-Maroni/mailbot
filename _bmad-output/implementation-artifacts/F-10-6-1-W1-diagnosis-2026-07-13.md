# F-10-6-1-W1 — Diagnosis (measurement-first pass, 2026-07-13)

**Context:** Epic 10.6 partial retro (2026-07-13) Adam D1 put F-10-6-1-W1 (qwen-on-CPU >30s tool-call timeout) *inside* done-flip clause 3 ("cheap lane REACHED ≠ usable"). Adam chose **diagnose-first, scope-after-data**. This is that diagnosis.

**Method:** probed the live `mailbot-ollama` container (Qwen 2.5 3B Q4_K_M, CPU-only, `ollama ps` empty at start = evicted) from inside `mailbot-api` via httpx against `http://ollama:11434/api/chat`, using Ollama's own server-reported nanosecond timings (`load_duration`, `prompt_eval_duration`, `eval_duration`, `prompt_eval_count`). Full-context runs used a synthetic but realistic 11-tool surface + inflated system prompt = **1658 input tokens**, matching the real Hermes turn shape.

## Measurements

| # | Scenario | wall | load (cold) | prompt_eval (INGEST) | input tok | eval (gen) | tool pick |
|---|----------|------|-------------|----------------------|-----------|------------|-----------|
| 1 | COLD trivial | 5.2s | **4048ms** | 383ms | 30 | 589ms | — |

## Findings

1. **The ~20s is PROMPT INGEST, not generation and not model load.** Run 3: 18.9s of the 22.5s is `prompt_eval` (ingesting 1658 tokens at ~11ms/tok — the going rate for a 3B model on CPU). Generation is only ~3.5s; cold-load is ~4s. **Latency is dominated by the size of the Hermes prompt, processed from scratch.**

2. **`num_ctx` is a RED HERRING — measured irrelevant.** The pre-diagnosis hypothesis (default context window too small → truncation/re-eval) was WRONG. 1658 tokens fits the default window; forcing `num_ctx=8192` changed ingest by ~0 (18925ms → 19061ms). **Do NOT "fix" num_ctx.** (Good example of why we measured instead of shipping the guess.)

3. **SMOKING GUN — the prompt cache. Run 5: identical prompt on repeat = 22.5s → 3.7s** because Ollama reused the ingested KV cache (`prompt_eval` 18925ms → 97ms). The 20s hit lands **only when the ingested prefix is cold** — i.e. when the model was evicted or the prefix changed. Warm + cached, the exact same full-context tool-call turn is **3.7s, comfortably under any budget.**

4. **The model is being EVICTED between turns.** `ollama ps` was empty at probe start; the adapter (`models.py:517` `ollama.AsyncClient(host=base_url)`; `chat_kwargs` at `:638`) sets **no `keep_alive`**, so Ollama's default 5-minute idle eviction applies. Eviction pays the ~4s cold-load AND throws away the prompt cache → next turn re-ingests 1658 tokens from scratch (the 18.9s). This is the mechanism that makes real turns cross 30s.

5. **Tool-selection fidelity was FINE in this probe** — all full-context runs picked `find_emails` correctly (contrast the walk's `pull_pending_notifications` mis-pick). Not reproduced here; possibly prompt-shape-dependent. Not the latency cause; noted, not chased.

## Reframed root cause

Not "qwen-on-CPU is too slow." The real cause: **we re-ingest a ~1658-token prompt from a cold cache on turns because the model isn't kept resident (`keep_alive` unset) and, secondarily, the prompt is large (~11ms/tok × 1658 = ~19s to ingest cold).** Warm + cached the same turn is 3.7s.

## Live fix-confirmation (keep_alive=-1 tested against the real container, 2026-07-13)

Directly tested the Seam-A hypothesis before writing code — same probe method, `keep_alive: -1` added:

| Call | Scenario | wall | prompt_eval (INGEST) |
|------|----------|------|----------------------|
| 1 | cold, first call (pins model) | 25.3s | 18598ms |
| 2 | **same prompt, model pinned** | **3.4s** | **84ms** |
| 3 | **shared system+tools prefix, DIFFERENT user tail** (chained-call sim) | **4.4s** | **164ms** |

- `ollama ps` after call 1 shows `UNTIL = Forever` — `keep_alive:-1` pins the model.
- **Call 2 confirms the cache-hold** — pinning preserved the prompt cache; ingest 18598ms → 84ms.
- **Call 3 is the load-bearing proof** — a new user message still cache-hit (164ms) because the expensive shared prefix (system + 11 tools) was reused. **This IS the chained-tool-call case inside a real Discord turn.** Calls 2..N are each ~3-4s.

**Consequence:** a real multi-call turn goes from `~20s + ~20s + ~20s → 502` to `~20s (cold first) + ~4s + ~4s → well under a 120s budget`. **Seam A (`keep_alive`) alone likely clears the budget.** Seam B (trim tool surface / prefix-stability) drops from load-bearing to *polish on the single cold first-call* — a meaningful de-risk of Story 10-6-4.

## Solution space (ranked by the data)

| Lever | Seam | Data support | Effort |
|-------|------|-------------|--------|
| **Set `keep_alive`** (pin model resident, e.g. `-1` or `30m`) | adapter `chat_kwargs` / client, `models.py:638` | **Strong** — kills eviction cold-load + preserves prompt cache across turns; biggest real-world win | Trivial |
| **Trim Hermes tool surface + system prompt** | Hermes-config (persona side) | **Strong** — ingest is linear in tokens; 1658→~800 ~halves the cold ~19s | Medium |
| **Stable prompt PREFIX** (tools+system invariant, first) | Hermes-config / dispatch | **Strong** — maximizes cross-call cache reuse within a chained turn (only first call pays full ingest) | Medium |
| **Bump adapter timeout 30s→~90-120s** (`registry.py:52,64`) | adapter | tolerance for the first cold-ingest call; band-aid, still needed | Trivial |
| **Tame Hermes retry ladder on timeout** | Hermes-config | Strong — a timeout is not transient; 3 retries = 3× the cold-ingest wait | Low |
| ~~`num_ctx`~~ | — | **REJECTED — measured irrelevant** | — |
| GPU / faster host | infra/deploy | Removes it entirely, but ties to CP-1 (not current priority) | Infra |

## Recommended scope for the follow-up

**Config-tuning is likely sufficient — no model swap, no shim, no hardware.** Minimal viable fix: `keep_alive` (adapter) + timeout bump (adapter) + retry-tame (Hermes) — all low-effort, gets warm turns to ~3.7s and cold turns tolerated. If cold-first-call latency is still unacceptable, add the structural prompt-trim (C) + prefix-stability. Because `keep_alive` + timeout live in `mailbot_api` (adapter) while trim/retry live Hermes-side, the clean cut is a small dev story (adapter config) that a re-walk validates; the Hermes-side trim can be a sibling if the adapter fix alone doesn't clear budget.

**Verdict for clause 3 (Adam D1):** the "usable" bar is achievable with config, not hardware. The cost thesis holds end-to-end — warm, a full tool-call turn is 3.7s.
