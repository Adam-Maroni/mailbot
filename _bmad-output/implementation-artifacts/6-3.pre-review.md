## Verdict

**MANDATORY-CR.**

4 criteria hit. The structural risk surfaces are unusually rich:

1. **Atomic claim correctness (concurrency safety).** The pull's `UPDATE notifications_outbox SET delivery_status='delivering' ... WHERE id=? AND delivery_status='pending'` predicate is the load-bearing race-safety mechanism. Two concurrent Hermes pollers MUST NOT return the same row. The test `test_pull_atomically_claims` exercises this serially via sequential pulls — does it ACTUALLY test concurrency? (Probably not — sequential pulls test the predicate, not the SQLite isolation level under simultaneous transactions.)
2. **5-attempt cap boundary off-by-one.** AC says "retries up to 5 times" then terminal. The SQL is `attempt_count < 5` for retry path and `attempt_count >= 5` for terminal. The pull's CLAIM bumps `attempt_count = attempt_count + 1`. So a fresh row hits ack at attempt_count=1 (under cap, retries → pending → next pull → attempt_count=2 → ...). The 5th pull bumps to attempt_count=5; the ack-failed path takes the terminal branch (>=5). So the row gets exactly 5 delivery attempts. Reviewer should walk this. Is "5 attempts" actually delivered or is it 4 or 6?
3. **Recovery loop vs ack race.** What if recovery reclaims a row (delivering→pending) RIGHT before an ack arrives? The ack's `WHERE delivery_status='delivering'` predicate matches 0 rows. The verb returns `ok=False` with `final_status='pending'`. The row stays pending; next pull bumps `attempt_count` again. This is correct but the attempt_count is now inflated relative to actual Discord-delivery attempts. Should there be a separate `discord_post_attempts` vs `claim_attempts` distinction? (Probably not for this story; flag for retro.)
4. **Legacy JSONL writer left in.** The OLD `notifications/__init__.py:send_urgent` JSONL writer is still callable (Task 7 "Decision point" chose to keep one epic). Is there ANY remaining production caller? `grep send_urgent` finds only the import and the function itself; all 4 originally-identified call sites were migrated. So it IS effectively dead code now. Should the dev have deleted it instead?
5. **Drainer Tier-2 routing change.** Previously: Tier-2 failures went to `send_urgent` with an `intended_notification_tier='important'` log flag. Now: they go to actual `send_important`. The behavior change is correct per AC but Adam won't see Tier-2 failures in real-time anymore — they wait for the 08:00 digest (Story 6-5). Is this what Adam wants? Or should it be a Tier-2-failures-go-urgent operational override?
6. **Recovery loop runs even when DB is empty.** The 10s interval fires regardless of whether any notifications exist. SQLite UPDATE-with-WHERE on an empty table is fast (microseconds) but it's still 6 queries per minute. Worth observing in `mailbot status` output as a "tick rate" metric. Out of scope for this story.
7. **MCP wrapper for `ack_notification` accepts `delivery_status: str`** with no Literal validation at the wrapper. The verb itself validates (`Literal["ok", "failed"]`) but the wrapper hides this. A malformed `delivery_status='partial'` from Hermes would reach the verb's `if delivery_status == "ok"` branch (no match) then the implicit-else `else: # delivery_status == "failed"` branch — surface-handling differs. Should there be wrapper-level validation?
8. **`pull_pending_notifications` returns a list of Pydantic-claimed rows BUT the claim is not transactional with the read.** Walk the order: `fetchall` (read), then per-row `execute_write` (claim), then per-row `fetchone` (re-read claimed state). Between the `fetchall` and the first claim, another process could insert and the new row would not be in this pull. That's fine. Between two claims, another process could pull-and-claim the second row first — our second claim would return rowcount=0 and skip. So the worst case is "we return fewer rows than requested." Acceptable. But not transactional. Worth documenting in the verb docstring.
9. **`tests/integration/test_spend_chart_command.py` assertion was relaxed from `== 17` to `>= 17`.** This is a real downgrade in test specificity. The author argues "prevent test churn" — but the original assertion was a useful canary. Should there have been a separate, more general "tool count grows as expected" test instead of relaxing the specific one?
