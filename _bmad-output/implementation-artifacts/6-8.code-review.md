## 2. Summary

The verb implementation itself (window math, chart rendering, `try/finally` symmetry) is solid, and the `_MATPLOTLIB_PYPLOT_ALLOW` boundary structure is correct. However, there is a blocking MCP transport bug: `RenderSpendChartOut.image_bytes: bytes` cannot be serialized to JSON by pydantic-core when the bytes are non-UTF-8 (i.e., all real PNGs), which means every live `/spend` invocation via the MCP transport will crash at the serialization boundary. There are also two flaky clock-dependent test cases and a missing regression fixture for the new boundary rule.

### HIGH-1 — PATCH — `mailbot_api/verbs/analytics/render_spend_chart.py:52` + `mailbot_api/mcp_server.py:544–564`

**Severity:** High
**Type:** PATCH

**Issue:** `RenderSpendChartOut.image_bytes` is typed as bare `bytes`. Pydantic v2 (`pydantic==2.13.1` in this project) serializes `bytes` fields to JSON by attempting UTF-8 decode. PNG bytes start with `\x89PNG...` (non-UTF-8), so `pydantic_core.to_json(result, fallback=str, indent=2)` — which is exactly what FastMCP's `_convert_to_content` calls on the tool return value — raises `PydanticSerializationError: Error serializing to JSON: invalid utf-8 sequence of 1 bytes from index 0`. This means **every** real `/spend` MCP call crashes at the protocol serialization step, not at the verb. Reproduced:

```python
>>> pydantic_core.to_json(RenderSpendChartOut(image_bytes=b'\x89PNG...', ...), fallback=str, indent=2)
PydanticSerializationError: Error serializing to JSON: invalid utf-8 sequence of 1 bytes from index 0
```

The unit/integration tests do not catch this because they call the verb directly (getting back `RenderSpendChartOut` in Python) — they never exercise the FastMCP serialization path that fires during a real MCP round-trip.

**Suggested fix — two options (DECISION needed for AC-alignment, see HIGH-2):**

Option A — `Base64Bytes` annotation (lowest-friction, Pydantic v2 native):
```python
from pydantic import Base64Bytes, BaseModel

class RenderSpendChartOut(BaseModel):
    mime_type: Literal["image/png"] = "image/png"
    image_bytes: Base64Bytes   # serializes as base64 string in JSON
    period: str
    total_usd: float
    task_count: int
    top_task: str
```
The verb populates it with raw bytes (Pydantic accepts raw `bytes` input and auto-encodes). The MCP consumer (Hermes) receives a base64 string and decodes before posting to Discord. The unit tests currently assert `result.image_bytes.startswith(b"\x89PNG")` — they continue to work because `Base64Bytes` keeps raw bytes at the Python layer; only JSON serialization changes.

Option B — MCP `Image` content type: return an `mcp.types.ImageContent` from the wrapper instead of the Pydantic model. FastMCP natively handles `Image` and produces a proper `image/png` base64-encoded content block. This is the "right" MCP idiom for binary blobs and avoids the base64-at-rest smell, but requires a structural change to the wrapper in `mcp_server.py`.

**Reasoning:** Without this fix the tool produces a `ToolError` on every real dispatch. The existing tests pass only because they bypass the MCP transport layer.

### HIGH-2 — DECISION — `mailbot_api/verbs/analytics/render_spend_chart.py:57` (missing `top_task_usd` field)

**Severity:** High
**Type:** DECISION

**Issue:** The AC specifies the text summary line: `"$X.XX spent {period}. Top task: {top_task} (${Y.YY}). Cap: $30."` The `${Y.YY}` is the cost of the top task. `RenderSpendChartOut` exposes `top_task: str` (the name) and `total_usd: float` (the total), but NOT the cost of the top task. SKILL.md Turn structure 4, step 2 works around this by calling `cost_breakdown(period="month")` as a sibling MCP call — but:

1. `cost_breakdown` only supports `period="today"|"month"` (from Story 2-10 `cost.py`). For `/spend week`, there is NO sibling call that can retrieve the top-task cost, so the `${Y.YY}` slot is unfillable.
2. The sibling-call workaround adds a second MCP round-trip per `/spend` invocation, which degrades the interaction.

**Suggested fix:** Add `top_task_usd: float` to `RenderSpendChartOut`. The verb already has the data — `rows[0][1]` is the top task's cost after `rows.sort(key=lambda r: r[1], reverse=True)`. It's a one-line addition:
```python
class RenderSpendChartOut(BaseModel):
    ...
    top_task: str
    top_task_usd: float = 0.0  # cost of top_task; 0.0 when task_count == 0
```
And in `render_spend_chart`:
```python
top_task_usd = rows[0][1] if rows else 0.0
return RenderSpendChartOut(..., top_task=top_task, top_task_usd=top_task_usd)
```

**Reasoning:** Without this field, the AC-2 summary line `"${Y.YY}"` can only be produced for `today/month` (via `cost_breakdown` sibling call) and cannot be produced for `week`. The field is already computed — it's just not surfaced.

### MED-1 — PATCH — `scripts/check_boundaries.py:526–538` (missing `from matplotlib import pyplot` bypass)

**Severity:** Med
**Type:** PATCH

**Issue:** The `_MATPLOTLIB_PYPLOT_ALLOW` boundary check covers:
- `import matplotlib.pyplot` (via `ast.Import`, line 455)
- `from matplotlib.pyplot import ...` (via `ast.ImportFrom`, line 529)

But it does NOT cover the alias import form:
- `from matplotlib import pyplot` → `full_mod = "matplotlib"`, `alias.name = "pyplot"`
- `from matplotlib import pyplot as plt` → same

This is exactly the bypass pattern that was previously handled for the verbs boundary (`from mailbot_api import verbs` — line 504). Verified via AST inspection: `ast.parse("from matplotlib import pyplot as plt")` yields `ImportFrom(module='matplotlib', names=[alias(name='pyplot', asname='plt')])`. The boundary check never fires on this form.

**Suggested fix:** After the existing pyplot `ImportFrom` check (line 526–538), add:
```python
# Indirect bypass: `from matplotlib import pyplot [as plt]`
if full_mod == "matplotlib" and rel not in _MATPLOTLIB_PYPLOT_ALLOW:
    for alias in node.names:
        if alias.name == "pyplot":
            violations.append(
                _violation(
                    node.lineno,
                    "`from matplotlib import pyplot` (indirect bypass)",
                    _MATPLOTLIB_PYPLOT_ALLOW,
                )
            )
```

**Reasoning:** Without this guard, any module can write `from matplotlib import pyplot as plt` and bypass the pyplot isolation boundary with no lint-time warning.

### MED-3 — PATCH — `tests/integration/test_spend_chart_command.py:116` (clock-dependent perf test)

**Severity:** Med
**Type:** PATCH

**Issue:** `test_render_spend_chart_perf_under_2s_at_1000_rows` seeds 1000 rows using `base_ts = now - timedelta(minutes=29)` and calls `render_spend_chart("today", ...)`, then asserts `out.task_count == 4`. When the test runs in the first 29 minutes of a UTC day (00:00:00Z – 00:29:00Z), `base_ts` lands on the previous day, and ALL 1000 rows fall outside the `today` window. The verb returns `task_count == 0` (empty path), the assertion `out.task_count == 4` fails, and the rendering path is not actually exercised — the test silently measures `_render_empty_png()` time instead of `_render_bar_chart_png()`.

**Suggested fix — use `period="month"` instead of `period="today"`:
```python
out = await render_spend_chart("month", db_path=db_path)
assert out.task_count == 4  # safe any day of the month if seeded within last 29min
```
Or change the seed to anchor within the current month unconditionally:
```python
base_ts = now.replace(day=1, hour=0, minute=30, second=0) + timedelta(minutes=1)
```
Or document the window as `period="week"` (always safe — rows 29 min ago are always within a 7-day window).

**Reasoning:** The test is nominally green but fails between 00:00 and 00:29 UTC and also exercises the wrong rendering path (empty vs bar chart) in that window. CI on a UTC-midnight schedule or manual runs just after midnight will surface the failure.

### MED-4 — PATCH — `tests/unit/verbs/analytics/test_render_spend_chart.py:188` (flaky month-boundary test)

**Severity:** Med
**Type:** PATCH

**File:line:** `tests/unit/verbs/analytics/test_render_spend_chart.py:188`

**Issue:** `test_period_month_includes_current_month_rows` seeds a row at `now - timedelta(hours=1)` and asserts `task_count == 1`. When the test runs on the FIRST DAY of a month before 01:00 UTC, `one_hour_ago` falls on the LAST DAY of the previous month — outside the `month` window (which starts at `YYYY-MM-01T00:00:00Z`). The assertion `task_count == 1` fails.

The comment in the test says `"1 hour ago — safe even on month-boundary midnight runs"` but this is incorrect: it's only safe from 01:00 UTC onward on the first day of each month.

**Suggested fix:** Seed the row with `ts = now.replace(day=1, hour=1, minute=0, second=0) + timedelta(hours=1)` to guarantee the row is always post-midnight on day 1. Or seed with `now` (no ts argument) which is always within the current month:
```python
await _seed(_fresh_db, task_type="summary_short", cost=0.50)  # default = now, always within this month
```

**Reasoning:** Flaky test that fails 1/720 of the time (00:00-01:00 on the 1st), which is hard to diagnose and will silently pass most of the time.

## 4. Non-Issues (dev brief items confirmed clean)

- **`plt.close(fig)` symmetry:** Both `_render_empty_png` (line 103–117) and `_render_bar_chart_png` (line 134–162) wrap all rendering in `try/finally: plt.close(fig)`. Symmetry confirmed.
- **`datetime.now(timezone.utc)` DST-immunity:** All `datetime.now()` calls use `timezone.utc`. No naked `datetime.now()` or `datetime.utcnow()` in the verb. Clean.
- **`import matplotlib.pyplot` allowlist scope:** The `ast.Import` and `ast.ImportFrom` branches both correctly fire on `matplotlib.pyplot` and `matplotlib.pyplot.*` forms. The gap is only the indirect `from matplotlib import pyplot` form (see MED-1).
- **F6 carve-out scope discipline:** No stray TODO comments, no half-finished Hermes glue, no sketched dispatcher code in any of the new files. The carve-out is clean.
- **SKILL.md narrative consistency:** The new "Slash-command verbs" section correctly lists `cost_breakdown`, `reset_degraded_mode`, `pause_router`, `resume_router`, `mute_category`, and `render_spend_chart`. The stale "NOT MCP-exposed" passage was correctly reworded. No dangling forward-references to Story 5-6 wiring that "hasn't shipped."
- **`week` rolling-window UX:** The `week` window is rolling (7 days back from `now`), not ISO-week-start. This is documented in the `_period_window_start` docstring. Consistent with the story's explicit decision. Acceptable — and `/spend week` users would likely expect "last 7 days" more than "this Mon–Sun."
- **`period=None` from FastMCP:** The `render_spend_chart` wrapper in `mcp_server.py` has `period: str = "month"`. FastMCP's JSON schema generation will mark this field as optional with default `"month"`. An omitted `period` gets the default; a JSON `null` would coerce to the Python default for a `str`-typed parameter. The verb's `_period_window_start` has an explicit `ValueError` guard for invalid values, including `None`-coerced strings. Safe.
- **Pydantic `mime_type: Literal["image/png"] = "image/png"` default:** FastMCP serializes this correctly as a constant string. No issue.
