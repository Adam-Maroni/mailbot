## 4. Key Insights

1. **Gate-coverage-only has a "story type" boundary, not just a "boundary-introducing" boundary.** Epic 2 retro framed CR cadence as "boundary-introducing / dep-introducing / dev-self-flagged / capstone." Epic 3 reveals a second axis: *privacy-invariant surfaces* and *load-bearing-orchestrator surfaces* also merit CR even when they don't introduce a new boundary. Story 3-3's Router precondition is the FR-2.3 hard invariant — privacy-invariant. Story 3-5's pipeline is the load-bearing path for every derivation forever — load-bearing-orchestrator. The Epic 2 cadence policy needs a v2 with these two additional axes.
2. **The boundary-test canonical pattern is now mature enough to be a one-paragraph checklist.** Three reuses (Story 3-1 idempotency, Story 3-3 yaml extension, Story 3-4 embedding) — all with the same shape: violation fixture, positive-pass (allowlisted-path-passes), specificity (benign-sha256 / benign-yaml usage), f-string bypass (`ast.JoinedStr`), keyword-arg bypass (post-CR-5 for 3-1). This is now codifiable as a writer-monopoly recipe in `architecture.md`. Same shape as the "audit-write-failure-masks-original-error" discipline from Epic 2.
3. **Defense-in-depth is the right shape for privacy invariants.** Story 3-3's FR-2.5 enforcement at BOTH startup AND per-call is the canonical example. The startup check catches drift-at-boot; the per-call check catches drift-from-hot-reload. Neither alone is sufficient (startup misses hot-reload, per-call misses misconfigured production deploys before any call lands). For FR-5.7 / NFR-PRIV-2 (no API for confidential admits-no-override), Epic 4's confirmation-token handshake should follow the same defense-in-depth shape: token-mint validation at one layer + token-consume validation at the dispatch layer.
4. **Disposition discipline (Story 3-1's "schema is largely already shipped by 001_init") avoids over-spec churn.** Story 3-1 was specified as if 001_init had not already shipped the derived-field columns. The dev pass discovered that 001_init already had them, and the actual delta was the W-5 companion columns + 3 missing indexes + the idempotency helper + the boundary check. Story 3-1's Disposition section documents this transparently. **The disposition-as-first-class-section pattern (Story 3-1 + Story 3-3 both used it) is the right way to handle spec-vs-reality drift mid-implementation.** Encode it in the story template.
5. **Cross-story integration gaps need a pre-implementation "wire-up checklist."** Story 3-5's `run_batch` should wire `enrich_sender` / `enrich_thread`. It didn't. The Epic 2 retro action #2 (downstream Literal/regex checklist) catches Literal-set widening; this is the same shape for cross-module wiring. Forward: a story that ships primitives consumed by ANOTHER story in the same epic should explicitly list the wire-up call sites in the *consumer's* Dev Notes, with a checkbox the consumer must tick.
6. **Sensitivity-aware digest is the canonical shape for any cross-email synthesis.** Story 3-7's `_format_email_for_digest` is the template: confidential excluded entirely, sensitive metadata-only, normal body-preview. Any future cross-email task (Epic 5 chat-resolution, Epic 7 corpus building) MUST reuse this filter. Codify in `architecture.md` as a Rule (call it Rule G: "every cross-email aggregation passes through the sensitivity-aware digest filter").
7. **Storing the just-written value in memory (Story 3-5 Dev Notes "Why store the JUST-WRITTEN `class_coarse` value in memory") is the right reflex.** The orchestrator avoided a DB round-trip by reading `RouterResult.output.class_coarse` instead of re-querying. Pattern reuse opportunity for any orchestrator-style code path. (Counter-pattern: when there's a real risk of intervening writers, the round-trip is the correct cost. For a single-orchestrator pipeline with no concurrent writers between steps, the in-memory carry is free.)
