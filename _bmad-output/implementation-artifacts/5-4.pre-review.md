The dev pass did not verify this against `nousresearch/hermes-agent:latest`'s actual config-loader. If Hermes uses a different substitution syntax (e.g., `{{VAR}}`, `<VAR>`, or no interpolation at all and the operator is expected to render the YAML via envsubst before mount), the config will fail at container startup. Mitigation: the AC explicitly notes this is the assumed contract; Phase 3.5 live-Discord verification will surface the failure mode if it's wrong. Story 5-2's `MAILBOT_SKIP_MCP` pattern shows a similar "verify against the image" footnote.
- [LOW] Path `/opt/data` is per architecture.md line 1031, but the Hermes image's documented contract was not directly verified. If Hermes actually reads config from `/etc/hermes/` or expects a `HERMES_CONFIG_PATH` env var, the bind-mount will land in the wrong place and the container will use built-in defaults silently. The AC notes this as an unverifiable-without-running-the-image case and accepts `/opt/data` as the default.
- [LOW] `gateway.discord.intents` is hand-listed with 4 strings. If `hermes-agent` expects a different intent-naming convention (e.g., camelCase or numeric flags), Discord will reject the bot's gateway connection. Verified at AC-1 design time against Discord's documented intent names (these are the standard names); the image is expected to translate to its own internal representation.
- [LOW] The `fallback_providers` entry exposes the Anthropic key to the Hermes container's env. This is intentional per NFR-OPS-6 but represents the documented break from Rule F.1. Inline comments + `.env.example` warning surface this; reviewer should sanity-check whether the rationale is sufficient.
