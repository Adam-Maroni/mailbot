## Dev Notes

### Container vs host invocation contract

All 3 walks use `docker compose exec -T mailbot-api python -m benchmark.*` rather than host-side `python -m benchmark.*` because:

- The container has `MAILBOT_DB_PATH=/data/mailbot.db` pre-set (per `docker-compose.yml:133`), so `benchmark.runner._resolve_db_path` resolves without `--db-path`.
- The container has `ANTHROPIC_API_KEY` from `.env` propagated to the process env (Rule F.1).
- The corpus + anchors are bind-mounted read-only into `/app/evals/` at `docker-compose.yml:119-120`; the container reads from there.
- The SQLite DB at `/data/mailbot.db` is in the `mailbot_db` named volume; container has direct fs access.
- Host-side would require: matching Python + frozen deps, ANTHROPIC_API_KEY env-pass, MAILBOT_DB_PATH pointing at the volume (which requires either `docker volume inspect` gymnastics OR running against a copy of the DB, which loses the write-once-persistence property).

The `-T` flag disables pseudo-TTY allocation, which matters because `benchmark.runner._confirm_proceed` uses `input()` which reads from stdin — without `-T`, docker's tty behavior can suppress the prompt. With `-T`, the `--yes` flag becomes the ONLY way to auto-confirm; typing `y` interactively works but is fragile.

### Scorer dispatch pattern

`benchmark.runner` writes `benchmark_runs` rows (dispatch data — raw model output + tokens + cost + outcome). `benchmark.scorer` reads those rows and writes `benchmark_scores` rows (quality metrics per-item + per-task, using either objective classification metrics or subjective anchor-calibrated auto-eval via Opus).

**Critical:** the runner does NOT auto-invoke the scorer. If Adam runs `benchmark.runner` and then `benchmark.report` without a `benchmark.scorer` invocation in between, the report renders empty (no scores → no verdict → INSUFFICIENT_DATA verdict for every cell). This is a known Story 9-6/9-7/9-8 pipeline seam. The AC-5 walk MUST include the `benchmark.scorer --run-id <run_id>` invocation between `runner` and `report` for the verdict to render meaningfully.

For AC-4 (corpus walk on production routing), the scorer dispatch is OPTIONAL — AC-4's acceptance is on `benchmark_runs.status=completed` + cell count + cost, not on scored quality metrics. Adam MAY skip the scorer for AC-4 unless the walk-evidence file explicitly needs per-task quality numbers.

### Cost estimation vs reality — the ±20% sanity check

Story 9-6's cost estimation (`benchmark/runner._estimate_total_cost`) uses per-item input token counts × per-model input/output pricing constants at `_estimate_input_tokens`. Known limitations:

- Estimation does NOT model prompt caching effects (Story 2-6 ephemeral cache) — real cost may be LOWER than estimate if the same input tokens hit the cache repeatedly (unlikely for a corpus walk; the corpus deliberately diversifies content).
- Estimation does NOT model rate-limit retries (Story 2-5 lane semaphore + retry chain) — real cost includes retries but the retries themselves don't add tokens; if the estimate is accurate on happy-path tokens, retries are cost-neutral.
- Estimation assumes worst-case output token generation up to `max_tokens_out` per task — actual output may be shorter for tasks that stop early.

**Interpretation:** actual < estimate by 10-40% is common on well-cached corpora, uncommon on this walk (diverse corpus). Actual > estimate by 10-20% is possible for retry-heavy runs.
