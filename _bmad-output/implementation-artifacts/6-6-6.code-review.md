### MED-1 — f-string missing `f` prefix: Location header swallowed on test failure

**Severity:** Med
**Type:** PATCH
**File:** `tests/integration/test_mcp_mount_routing.py:145-147`

**Issue:**

```python
assert response.status_code != 307, (
    "POST /mcp/ returned 307 — the Mount path is misconfigured. "
    "Location: {response.headers.get('location')!r}. "   # <-- plain string, not f-string
    "Expected: handler reached directly on the trailing-slash URL."
)
```

The assertion message is a plain string concatenation, not an f-string. If the assertion fires (i.e., if the routing fix is reverted and `POST /mcp/` starts returning 307), the failure message will literally print `{response.headers.get('location')!r}` rather than the actual Location header value. The diagnostic information that would tell a developer WHERE the redirect is pointing is lost, making the failure significantly harder to diagnose.

**Suggested fix:**

```python
assert response.status_code != 307, (
    f"POST /mcp/ returned 307 — the Mount path is misconfigured. "
    f"Location: {response.headers.get('location')!r}. "
    f"Expected: handler reached directly on the trailing-slash URL."
)
```

**Reasoning:** This is a latent bug in a regression guard whose entire purpose is to surface routing failures with actionable information. The guard is functioning correctly for the passing case; the defect only manifests at the exact moment it would be most needed. It is a trivial fix but meaningfully degrades the diagnostic value of the most important E2E test.

### MED-2 — `mcp.startup.live` log event hardcodes `"path": "/mcp"`, misrepresenting effective Hermes-facing path

**Severity:** Med
**Type:** PATCH
**File:** `mailbot_api/main.py:226`

**Issue:**

```python
logger.info(
    "mcp server live",
    extra={"event": "mcp.startup.live", "tools": _EXPECTED_TOOL_COUNT, "path": "/mcp"},
)
```

The `path` field is hardcoded as `"/mcp"`. This was accurate before this story because Hermes's configured URL was `http://mailbot-api:8000/mcp` (no slash). After Story 6-6.6 Part B, Hermes now contacts `http://mailbot-api:8000/mcp/` (with trailing slash). The log event will now confuse an operator reading the startup logs: the path logged is `/mcp` but the MCP handler's effective entry point — the URL Hermes actually POSTs to successfully — is `/mcp/`. If an operator is diagnosing a future F6-class regression and searches the logs for the path, the hardcoded `/mcp` does not distinguish between the pre-fix and post-fix state.

More precisely: the `streamable_http_path` is now `"/"` (inner route), mounted at `/mcp` (outer Mount prefix). The path that Hermes actually uses is `/mcp/`. The log should reflect the externally-visible URL shape, not the FastAPI Mount path label.

**Suggested fix:**

```python
logger.info(
    "mcp server live",
    extra={
        "event": "mcp.startup.live",
        "tools": _EXPECTED_TOOL_COUNT,
        "mount_path": "/mcp",
        "hermes_url_path": "/mcp/",  # trailing slash required per Story 6-6.6 Part B
    },
)
```

Alternatively, surface the `streamable_http_path` setting dynamically:

```python
logger.info(
    "mcp server live",
    extra={
        "event": "mcp.startup.live",
        "tools": _EXPECTED_TOOL_COUNT,
        "path": "/mcp/",  # full path Hermes POSTs to (trailing slash per Story 6-6.6)
    },
)
```

**Reasoning:** Observability log events are the primary diagnostic surface for production incidents. The `path` field in `mcp.startup.live` is now stale and will mislead operators reading startup logs after the fix. This is particularly acute because F6's symptom (MCP discovery failure) would prompt an operator to inspect exactly this log event; the mismatch between logged path and configured URL makes the fix appear not to have applied.

### LOW-1 — `test_post_to_mcp_no_slash_redirects_or_serves` has tautological Location guard

**Severity:** Low
**Type:** PATCH
**File:** `tests/integration/test_mcp_mount_routing.py:185`

**Issue:**

```python
assert loc.endswith("/mcp/") or loc.endswith("/mcp/"), (
```

Both branches of the `or` are identical (`loc.endswith("/mcp/")`). This is a no-op tautology — the second branch can never differ from the first. Almost certainly the intent was `loc.endswith("/mcp/") or loc == "/mcp/"` (checking both relative and absolute Location header forms), or `loc.endswith("/mcp/") or loc.endswith("/mcp")` (with and without trailing slash). As written, the guard does not cover any case the left branch doesn't already cover.

**Suggested fix:** Clarify the intent. If the goal is to handle both relative and absolute Location headers:

```python
assert "/mcp/" in loc, (
    f"307 Location is {loc!r}, expected to contain `/mcp/`. "
    "F6 redirect chain has changed shape."
)
```

Or if both slash/no-slash are acceptable destination paths:

```python
assert loc.endswith("/mcp/") or loc.endswith("/mcp"), (
    f"307 Location is {loc!r}, expected ending in `/mcp/` or `/mcp`. "
    "F6 redirect chain has changed shape."
)
```

**Reasoning:** The tautology means the Location-header guard is weaker than it appears. It would not catch a redirect to `/other-path/` or an empty Location header. Low severity because `test_post_to_mcp_no_slash_redirects_or_serves` already asserts non-404, so the guard is a secondary check inside a `if response.status_code == 307:` branch that only fires in the edge case.

### LOW-2 — `docs/setup-vps-runbook.md` has no mention of F6 / trailing-slash URL shape requirement

**Severity:** Low
**Type:** DEFER
**File:** `docs/setup-vps-runbook.md` (entire file; no specific line)

**Issue:**

The runbook covers §1 pre-requisites through §9 validation gates. It has no mention of the F6 routing constraint: that `hermes-config/config.yaml`'s `mcp_servers.mailbot-api.url` MUST include a trailing slash (`/mcp/` not `/mcp/`). An operator following the runbook on first VPS deploy who edits `hermes-config/config.yaml` by hand (e.g., to update the base host) could accidentally drop the trailing slash and re-introduce the client-side half of F6. The error they would observe (`MCP server 'mailbot-api' initial connection failed`) is hard to diagnose without knowing the slash is load-bearing. `scripts/check_hermes_config.py` would catch it, but the runbook doesn't surface that script at the deploy-config step.

The pre-review self-audit (surface 7) noted this gap and labelled it DEFER-worthy if not addressed in this story.

**Suggested fix:** Add a note to `docs/setup-vps-runbook.md` §3 (Populate `.env`) or add a new §3.5 (Hermes config shape) with:

> The `hermes-config/config.yaml` file ships pre-configured. One value is load-bearing and easy to break inadvertently: `mcp_servers.mailbot-api.url` MUST end with a trailing slash (`http://mailbot-api:8000/mcp/`). Without it, Hermes's MCP client receives a 307 redirect it cannot follow, and all 17 MCP tools fail to register at startup. Run `python scripts/check_hermes_config.py` to validate before `docker compose up`.

**Reasoning:** The `check_hermes_config.py` script provides a safety net, but only if the operator knows to run it. The runbook is the operator's primary reference during first deploy; the gap means F6-class regressions are one accidental config edit away with no in-path warning. Deferring to Story 6-7's runbook scope is defensible (it shipped already), but a one-paragraph addition to the existing runbook in this story would close the gap with minimal effort.

## 4. Probe results against pre-review's 7 structural risk surfaces

**Surface 1 — Two-part fix interdependence matrix:**
- Server-side-only revert (keep trailing-slash URL, drop `streamable_http_path="/"` kwarg): `test_streamable_http_app_inner_route_is_root` FAILS (inner route back to `/mcp`, assertion fires). `test_post_to_mcp_trailing_slash_reaches_handler_not_404` also FAILS (POST `/mcp/` → Mount strips `/mcp` → inner path `""` → inner Route at `/mcp` doesn't match → 404). Both halves caught independently. Coverage: adequate.
- Client-side-only revert (keep `streamable_http_path="/"`, drop trailing slash from config): `test_hermes_config_url_has_trailing_slash` FAILS. `test_hermes_config_mcp_servers_mapping_with_mailbot_api` in `test_hermes_config.py` also FAILS. `scripts/check_hermes_config.py` exits 1 with a specific message. Coverage: adequate.
- Verdict: the matrix holds. Each isolated failure mode is caught by at least one dedicated test.

**Surface 2 — FastMCP version-bump exposure:**
`requirements.txt` line 6 pins `mcp==1.27.2`. If FastMCP 2.x renames `streamable_http_path`, `test_streamable_http_app_inner_route_is_root` asserts `server.settings.streamable_http_path == "/"` — the attribute access would raise `AttributeError` before the assertion, failing the test (desired behavior). If the kwarg is removed from the constructor entirely, the FastMCP construction itself raises `TypeError`. Both cases produce CI signal. Adequate.

**Surface 3 — Mount + trailing-slash interaction; alternative not sketched:**
The inline comment block in `hermes-config/config.yaml` (lines 94-101) explains the why but does not sketch the alternative (`redirect_slashes=False`). This is acceptable — the comment correctly states the chosen fix and cites the constraint. The pre-review noted this but it is genuinely low value to document a rejected alternative in config YAML. No finding.

**Surface 4 — E2E test faithfulness (TestClient vs real container transport):**
The tests use httpx's `TestClient` (in-process), not a real container-to-container TCP connection. The dev acknowledged the `Invalid Host header: testserver` transport-security warning during testing. The tests are exercising FastAPI routing layer semantics, not TLS terminator or proxy behavior. This is a documented limitation and not a new finding — the tests are appropriate for what they claim to test (routing shape), and the inline docstrings are clear that they are not full-stack Hermes integration tests. The structural test (`test_streamable_http_app_inner_route_is_root`) is the most reliable anchor and does not have this limitation at all. No new finding beyond what the pre-review documented.

**Surface 5 — Hermes 307-follow assumption documentation:**
`hermes-config/config.yaml` lines 97-101 explicitly document: "Hermes's MCP client does NOT follow redirects on its bidirectional POST transport (gives up after 3 attempts)." `tests/integration/test_mcp_mount_routing.py` lines 8-13 also document it. If a future Hermes version follows 307s, the trailing-slash URL is still correct (no regression). Adequate.

**Surface 6 — `check_hermes_config.py` failure message specificity:**
`scripts/check_hermes_config.py:151-155` prints: `mcp_servers['mailbot-api'].url drift: expected 'http://mailbot-api:8000/mcp/', got '<actual>'`. This is specific and actionable — the expected vs actual values are both shown, and the expected value contains the trailing slash. An operator can diagnose F6-class URL breakage from this message alone. Adequate.

**Surface 7 — Setup-vps runbook gap:** Identified as LOW-2 above.

**Additional surface — `mcp.startup.live` log accuracy:** Identified as MED-2 above.

**Additional surface — 307 assert f-string bug:** Identified as MED-1 above.

**Additional surface — bearer-auth forward-compat interaction:**
The `Authorization: Bearer ${MAILBOT_ROUTER_KEY}` header in `hermes-config/config.yaml` is correctly documented as a forward-compat placeholder (lines 82-91). The F6 fix does not interact with this header at all: bearer-auth enforcement on the MCP mount is deferred to a future story, and the placeholder will continue to be ignored by mailbot-api's MCP handler regardless of the trailing-slash routing shape. When the bearer-auth gate ships, the trailing-slash URL is unaffected. No issue.
